# Build experiment results

## Compiler cache

The macOS host uses kache 1.0.0 through Cargo's `rustc-wrapper`. The cross-checkout rpath regression and its fix are recorded in [the baseline](build-baseline.md). The host-wide `kache stats` output combines other projects and is not a Player benchmark.

The [sccache architecture](https://github.com/mozilla/sccache/blob/main/docs/Architecture.md) uses a local server for both its server-side and client-side modes. The campaign forbids a new service, so the sccache pilot was not run or added. There are no sccache hit, miss, overhead, or timing results. This is a constraint-based omission, not evidence that sccache is slower.

## Development shell

The optional flake locks nixpkgs at the revision in `flake.lock`. Muon is 0.7.0, Meson 1.12.1, Samurai 1.3, Ninja 1.13.2, and pkgconf 3.0.10. The pkgconf source has the existing project's version and an ISC license. The Linux x86-64 pkgconf executable was 58,456 bytes and its Nix wrapper was 860 bytes in the test environment. These tools are development inputs and add no runtime dependency to the player.

Nix 2.35.4 evaluated both shell definitions with `nix flake check --no-build --all-systems`. The x86-64 Linux shell ran under emulation in a disposable Linux container. Its `pkg-config` resolved a controlled `.pc` file, and `make -n linux` expanded identically inside and outside the shell. The shell did not expose a C compiler in that container. The Linux player build remains in the existing Alpine container.

The macOS shell was evaluated but not entered on macOS because Nix is not installed there. Its use of the selected Xcode compiler and SDK still needs a native check. Nix's first shell setup fetched its closure and built pkgconf; provisioning time and disk use have not been measured. No Player artifact size, memory, startup, or build-time comparison has been attributed to the shell.

## Build measurements

The owner waived performance gates on 2026-11-10. The observations below were collected on the same macOS arm64 host, but under competing load: the one-minute load average was roughly 9–15 on ten logical CPUs during the native runs. The host state changed during later Rust runs. These numbers describe the runs; they do not establish a speedup under normal development conditions.

The reference for native dependencies was `ead8703`, the original revision plus the clean-prefix fix. The candidate was the **unaccepted** prototype at `campaign/build-cache` (`01ebc0c`), which still fails the direct Cargo validation requirement. Each used a separate empty prefix, warm copies of the same pinned source archives, Apple Clang, Homebrew Meson 1.12.1, and Ninja 1.13.2 through a `ninja -j 2` wrapper. `JOBS=2` was set; the wrapper enforces the actual Ninja limit. No native compiler cache was configured. Wall and child CPU times came from `/usr/bin/time -l`, with user and system CPU added. Copying the already-downloaded archives took 0.12 s and 0.11 s respectively on this filesystem; this is not cold network provisioning.

The five warm native runs alternated reference and prototype with the same tool environment. A first attempted warm prototype run changed `PATH` when the shell changed directories, selected a different Python, and began rebuilding SPIRV-Cross and libplacebo; it was interrupted and excluded. A direct invocation in the original environment then hit all six components. The prototype validates by hashing tools and component products, so its additional warm work buys checks the stamp-only reference lacks; it is not an equivalent integrity guarantee.

For the accepted-code release, `scripts/release.sh` used `CARGO_BUILD_JOBS=2`, `KACHE_KEY_SALT=player-benchmark-clean-release-20261110`, and the native settings above. The first release attempt on the reference compiled Rust but failed when the bundler tried to strip a read-only copied library. Commit `8874813` fixes that failure, restores the copied files' original modes after signing, and was verified with the real release gate and `codesign --verify --deep --strict`. The clean accepted-code run includes native compilation, Rust compilation and bundling; it excludes archive downloads and host tooling installation.

The development run used `scripts/build.sh`, `CARGO_BUILD_JOBS=2`, and a distinct `KACHE_KEY_SALT=player-benchmark-dev-20261110`. Its first build took 57.61 s wall and 108.55 s CPU. An unchanged second build took 0.38 s wall and 0.28 s CPU; it emitted no kache compiler events. The kache event log filtered to this checkout recorded two `miss` events and two compiler runs for the edited build, `player_app` and `player`. The clean release recorded 65 `dup`, 23 `miss`, and 8 `passthrough` events; `dup` events each recorded a compiler run, so they are not counted as cache hits. The initial development build recorded 72 `dup`, 16 `miss`, and 5 `passthrough` events. These event labels and counts describe kache's records, not a comparison against an uncached build.

After the development build and tests warmed that kache store, a build into a new `CARGO_TARGET_DIR` with the same salt took 9.90 s wall and 15.66 s CPU. Its checkout-filtered events recorded 32 `local_hit`, 6 `dup`, 1 `miss` and 4 `passthrough` results; the six duplicates and one miss each ran a compiler. The installed player reported the original help text, used this checkout's native and FFmpeg rpaths, and played the fixture. This exercises compiler-cache restoration into a fresh target; it is not equivalent to Cargo's unchanged local-target reuse or to a GitHub Actions restore.

The accepted-code release's `scripts/measure.sh final` reported a 1,699,056-byte executable, 14,693,984-byte executable-plus-framework closure and 69.95 MB median 1080p RSS; all of its size, memory, protocol, Lua and audio checks passed. The first attempt stopped because the isolated checkout lacked `audio-mp3.mp3`; the second used that fixture generated with the repository's exact recipe. The script exited 75 because its internal host check deferred timing checks. The owner waived the gate, but the reported timing samples remain subject to contention and are not a performance pass. Its revision label included `-dirty` because the separate development help-text experiment was still present; the release binary had been built and signed before that edit. After restoring the experimental edit, `scripts/audit.sh` passed its 16 FFmpeg, 7 build, 56 local-only and 20 release checks; it skipped the advisory scan because `cargo-audit` was not installed. `tests/run.sh suite` passed 458 checks, including Metal and Vulkan GUI gates. Its first fixture-generation attempt timed out while FFmpeg was waiting; the harness retried and succeeded, so that intermittent fixture issue remains unresolved.

Two independent macOS release builds of `8874813` used the same tools, build policy, two-job limits and warm source archives, but separate checkout paths, path-valued flags and distinct kache salts. The second completed in 88.01 s wall and 136.97 s CPU, and also passed all 20 release checks and strict signature verification. Their bundles had the same 16 paths, types, modes and symlink targets, but were not byte-identical: `player`, `libplacebo.387.dylib`, `Resources/build.json` and `CodeResources` differed. The other three bundled libraries and remaining files matched. The player had 79 differing bytes and libplacebo 48; all those differences lay in their Mach-O UUID or code-signature regions. The build stamp hashes the unbundled player, whose recorded hash differed; those unbundled binaries contain their respective absolute checkout rpaths. No artifact bytes were normalized, and this is not a claim of byte-reproducible releases.

The Linux dependency and application builds ran under x86-64 emulation in the pinned Alpine container as correctness checks; they are not comparable to native Linux CI timing. The image lacks kache and mold, so these runs supplied workspace-local kache 1.0.0 and mold 2.39.1, with a compiler wrapper selecting mold and the existing flags preserved. No additional cache service was started. The local Linux release script built the tarball and checked its checksum. A separate closure audit passed without the tool setup's `LD_LIBRARY_PATH`. The full `tests/run.sh suite` then passed 427 checks, including headless Wayland, playback, the Rust-link gate and the audit. The tested Linux inputs matched the accepted tree at `a7cb1f3`. Mold's local `.got` slots initially triggered a false static-FFmpeg finding; that commit limits the exception to local object slots in `.got`, and its regression fixture still rejects defined FFmpeg symbols elsewhere. The follow-up `7690535` was verified with the same real audit and a fixture that forces ELF inspection failures.

A second emulated Linux release build at the same revision, container path and tool settings used fresh target and kache directories. It stopped when `rustc` compiling `player-overlay` received `SIGBUS`. An isolated build of that crate with the same target and flags then succeeded. Disk and memory were available, but the signal's cause was not established; kache also warned that the workspace cache is on FUSE, which is not proof of the cause. No second tarball was produced, so Linux release reproducibility remains untested.

Under that emulation, isolated native dependency builds used Meson 1.12.1, Samurai limited to two jobs, the same compiler wrapper and warm source archives. `/usr/bin/time -v` inside the container measured the build process; an outer host timer also included the existing Docker image check and container startup. A clean reference prefix took 49.11 s inside (85.94 s CPU) and 51.58 s end to end; the unaccepted prototype took 51.15 s inside (87.57 s CPU) and 52.63 s end to end. These are single observations, not a speedup comparison.

Five alternating unchanged Linux builds had a 0.14 s median inside the reference container (0.14–0.15 s range), versus 1.50 s for the prototype (1.47–1.52 s). Including container startup, the medians were 1.33 s and 2.68 s. None compiled or installed products. The reference trusted stamps; the prototype validated the cached artifacts and tools. After the same blank-line edit inside the libplacebo recipe, the reference cleared its prefix and rebuilt all three components in 48.58 s inside (85.00 s CPU); the prototype reused Vulkan headers and Shaderc and rebuilt libplacebo in 50.67 s (87.21 s CPU). These are single contended emulated runs, but they show why a narrower closure alone is not evidence of a worthwhile improvement when libplacebo dominates the work.

A local restore simulation copied the prototype's complete Linux cache and prefix link to another checkout mounted at the same `/work` path. The filesystem copy took 0.36 s; validation and three hits took 1.72 s inside the container and 3.64 s including startup. After corrupting the copied Shaderc archive, the prototype detected the mismatch, reused Vulkan headers, rebuilt Shaderc and libplacebo, and restored the original archive hash. That rebuild took 51.51 s inside (88.03 s CPU). This exercises the unaccepted prototype only: it is not a GitHub Actions restore measurement, and the existing CI cache paths have not been adapted to this cache layout.

Native Linux timings and qualification, a restored CI-cache measurement, equivalent before/after Rust and release comparisons, and F1 qualification remain open.
