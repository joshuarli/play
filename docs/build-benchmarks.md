# Build experiment results

## Compiler cache

The macOS host uses kache 1.0.0 through Cargo's `rustc-wrapper`. The cross-checkout rpath regression and its fix are recorded in [the baseline](build-baseline.md). The host-wide `kache stats` output combines other projects and is not a Player benchmark.

An exploratory native pilot used the developer's kache fork at `722296bb` (`2.0.0-rc.2`), built in the debug profile. Its opt-in `KACHE_DAEMON_AUTOSTART=0` change was tested separately in the fork. The pilot pointed `CC` and `CXX` at isolated kache shims, used a 5 GiB local store, Meson 1.12.1, two-job Ninja and Apple Clang 21, and started no new daemon. Two successive changes to the Metal backend log string each forced the existing global-hash dependency script to rebuild. Both builds completed; the second library contained the new string and the rebuilt player loaded it. The second run recorded 52 local hits, 72 passthroughs, 15 skipped actions and three errors from `testfile.c` compiler probes. Passthroughs and skipped actions ran their compilers. After normalizing the checkout, prefix and compiler paths, all 63 SPIRV-Cross and libplacebo compilation commands and the libplacebo link command matched the uncached build. This checks the observed commands and output, not full ABI or release qualification.

The first run took 41.61 s wall and 67.53 s CPU; the warm-cache run took 23.27 s wall and 35.30 s CPU. These are single observations of different cache states under contention, with an unoptimized kache binary and no uncached control, so they do not establish a speedup. Native caching can recover some work after coarse invalidation, but it does not validate the installed prefix or fix the direct Cargo reader gap. The fork change remains on its isolated branch and has not been integrated into Player or CI.

The earlier native kache pilot and the five alternating pairs below did not record `SOURCE_DATE_EPOCH`. When it is unset, kache defaults wrapped C-family compilers to `SOURCE_DATE_EPOCH=0`. A later Apple Clang probe produced `Jan  1 1970` for `__DATE__` under that default and the current date directly; kache's `KACHE_CC_SOURCE_DATE_EPOCH=passthrough` matched the direct output. Those comparisons do not establish equivalent compiler environments and cannot justify adoption, even where their command-line arguments matched.

Five subsequent alternating macOS pairs changed the same Metal log string, ran the existing dependency script with either Apple Clang directly or the fork's compiler shims, and checked that the player loaded the newly built libplacebo. Both sides used one checkout, two Ninja jobs and warm archives. After removing the compiler executable from each command, all 63 compilation commands and the libplacebo link command matched. The direct builds had a 29.27 s median wall time and a 27.89–40.32 s range; kache builds had a 22.54 s median and a 21.90–38.16 s range. Median CPU times were 48.13 s and 34.46 s, with ranges of 46.12–65.62 s and 33.72–62.75 s. Load averages ranged from 2.95 to 4.43 on ten logical CPUs. The ranges overlap, the fork binary was unoptimized, and no independent profile established the limiter, so this is not an accepted speedup comparison.

Across the five kache runs, the event log recorded 211 local hits and 49 misses, plus 360 passthroughs, 75 skipped actions and 15 errors from compiler probes. Each miss, passthrough and skipped action ran a compiler; all dependency builds succeeded. The first paired kache run accounted for the 49 misses even though some resulting keys matched entries from the earlier warm run. Four later kache runs supplied the remaining hits. No daemon was started. This pilot measured dependency builds, not a release or a complete Rust edit workflow.

A later comparison used the fork through `c83f8d18` and Player `5707edb` in one isolated macOS arm64 checkout. Five counterbalanced pairs each changed a same-length Metal log string, ran `scripts/build-deps.sh` and then `scripts/build.sh`, and verified that the resulting player loaded the library containing the edit. Both sides used Apple Clang 21, Meson 1.12.1, two Ninja and Cargo jobs, warm archives, and the same Rust kache wrapper; only the native compiler shims differed. The fork used a 5 GiB local store and started no daemon. The sums of dependency and application subprocess times had a 40.80 s median and 31.24–48.02 s range without native kache, versus 38.01 s and 31.42–40.75 s with it. Corresponding CPU medians were 69.80 s and 62.08 s, with ranges of 53.26–81.45 s and 52.16–66.55 s. Paired wall-time differences ranged from a 0.18 s regression to a 10.01 s reduction. These totals exclude verification and benchmark orchestration. Load averages ranged from 3.94 to 5.75 on ten logical CPUs. The ranges overlap. In a separate uncached rebuild, samples of two Clang compiler processes showed C++ template instantiation and LLVM code generation, but did not profile the whole workflow or establish its limiter. This is an inconclusive end-to-end speed comparison.

Each native kache run recorded 72 local hits, one miss, 79 passthroughs and three errors from `testfile.c` compiler probes; all ten builds and runtime checks succeeded. The first recorded pair had identical 63 native compilation command lists; the link command was not compared in this run. The existing global hash still rebuilt the dependency prefix after each edit, and these results do not validate the component-cache prototype or release artifacts.

A further pilot used Player `97975f5` and kache fork `4f84c167` in separate macOS arm64 checkouts. Each of five pairs changed the same libplacebo Metal log string, then ran `scripts/build-deps.sh` and `scripts/build.sh`; the direct build ran first in each pair. Both sides used Apple Clang 21, Meson 1.12.1, two Ninja and Cargo jobs, warm source archives, warm caches, and the same Rust wrapper. `SOURCE_DATE_EPOCH` was unset, and kache used `KACHE_CC_SOURCE_DATE_EPOCH=passthrough` for C and C++; Objective-C used Apple Clang directly on both sides. The fork used separate bounded 5 GiB local stores and no new daemon. Across the five pairs, the sum of dependency and application wall times had a 31.338 s median and 31.259–31.477 s range directly, versus 22.628 s and 22.558–23.021 s with native kache. Combined CPU medians were 53.231 s and 35.415 s, with ranges of 53.101–53.263 s and 35.284–36.043 s. Load averages ranged from 1.99 to 2.78 on ten logical CPUs. These are observations for this edit and host, not a performance-gate pass or a CI result.

The five kache dependency builds recorded 322 local hits, 18 misses and 370 passthroughs; all builds succeeded. Both sides recompiled the same five Player crates after the native rebuild. After normalizing checkout roots and removing the compiler executable, all seven SPIRV-Cross and 56 libplacebo compile commands and the libplacebo link command matched. The final libraries had matching install names, linked-library lists and exported symbol names; each contained the edited string and each player loaded its own library and played one frame. These checks do not establish complete ABI or release equivalence. The unchanged reference still rebuilt the native prefix for each patch edit, so the measurement does not establish a benefit over a correct per-component cache.

Native kache remains experimental. Its default timestamp pin changes compiler behavior when the caller leaves `SOURCE_DATE_EPOCH` unset. Its passthrough mode preserves that environment but permits a time macro to change between preprocessing for the cache key and compilation, potentially storing an object under the wrong key. A diagnostic replay of the current 57 C and C++ translation units found no time-macro warning, but compiler diagnostic pragmas can suppress that warning, and the replay is not a proof for future or system inputs. Neither mode is accepted for the Player native build under the current compiler-behavior and cache-correctness requirements.

The [sccache architecture](https://github.com/mozilla/sccache/blob/main/docs/Architecture.md) uses a local server for both its server-side and client-side modes. The campaign forbids a new service, so the sccache pilot was not run or added. There are no sccache hit, miss, overhead, or timing results. This is a constraint-based omission, not evidence that sccache is slower.

## Development shell

The optional flake locks nixpkgs at the revision in `flake.lock`. Muon is 0.7.0, Meson 1.12.1, Samurai 1.3, Ninja 1.13.2, and pkgconf 3.0.10. The pkgconf source has the existing project's version and an ISC license. The Linux x86-64 pkgconf executable was 58,456 bytes and its Nix wrapper was 860 bytes in the test environment. These tools are development inputs and add no runtime dependency to the player.

Nix 2.35.4 evaluated both shell definitions with `nix flake check --no-build --all-systems`. The x86-64 Linux shell ran under emulation in a disposable Linux container. Its `pkg-config` resolved a controlled `.pc` file, and `make -n linux` expanded identically inside and outside the shell. The shell did not expose a C compiler in that container. The Linux player build remains in the existing Alpine container.

The macOS shell was evaluated but not entered on macOS because Nix is not installed there. Its use of the selected Xcode compiler and SDK still needs a native check. Nix's first shell setup fetched its closure and built pkgconf; provisioning time and disk use have not been measured. No Player artifact size, memory, startup, or build-time comparison has been attributed to the shell.
