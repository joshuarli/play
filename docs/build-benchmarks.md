# Build experiment results

## Compiler cache

The macOS host uses kache 1.0.0 through Cargo's `rustc-wrapper`. The cross-checkout rpath regression and its fix are recorded in [the baseline](build-baseline.md). The host-wide `kache stats` output combines other projects and is not a Player benchmark.

An exploratory native pilot used the developer's kache fork at `722296bb` (`2.0.0-rc.2`), built in the debug profile. Its opt-in `KACHE_DAEMON_AUTOSTART=0` change was tested separately in the fork. The pilot pointed `CC` and `CXX` at isolated kache shims, used a 5 GiB local store, Meson 1.12.1, two-job Ninja and Apple Clang 21, and started no new daemon. Two successive changes to the Metal backend log string each forced the existing global-hash dependency script to rebuild. Both builds completed; the second library contained the new string and the rebuilt player loaded it. The second run recorded 52 local hits, 72 passthroughs, 15 skipped actions and three errors from `testfile.c` compiler probes. Passthroughs and skipped actions ran their compilers. After normalizing the checkout, prefix and compiler paths, all 63 SPIRV-Cross and libplacebo compilation commands and the libplacebo link command matched the uncached build. This checks the observed commands and output, not full ABI or release qualification.

The first run took 41.61 s wall and 67.53 s CPU; the warm-cache run took 23.27 s wall and 35.30 s CPU. These are single observations of different cache states under contention, with an unoptimized kache binary and no uncached control, so they do not establish a speedup. Native caching can recover some work after coarse invalidation, but it does not validate the installed prefix or fix the direct Cargo reader gap. The fork change remains on its isolated branch and has not been integrated into Player or CI.

Five subsequent alternating macOS pairs changed the same Metal log string, ran the existing dependency script with either Apple Clang directly or the fork's compiler shims, and checked that the player loaded the newly built libplacebo. Both sides used one checkout, two Ninja jobs and warm archives. After removing the compiler executable from each command, all 63 compilation commands and the libplacebo link command matched. The direct builds had a 29.27 s median wall time and a 27.89–40.32 s range; kache builds had a 22.54 s median and a 21.90–38.16 s range. Median CPU times were 48.13 s and 34.46 s, with ranges of 46.12–65.62 s and 33.72–62.75 s. Load averages ranged from 2.95 to 4.43 on ten logical CPUs. The ranges overlap, the fork binary was unoptimized, and no independent profile established the limiter, so this is not an accepted speedup comparison.

Across the five kache runs, the event log recorded 211 local hits and 49 misses, plus 360 passthroughs, 75 skipped actions and 15 errors from compiler probes. Each miss, passthrough and skipped action ran a compiler; all dependency builds succeeded. The first paired kache run accounted for the 49 misses even though some resulting keys matched entries from the earlier warm run. Four later kache runs supplied the remaining hits. No daemon was started. This pilot measured dependency builds, not a release or a complete Rust edit workflow.

The [sccache architecture](https://github.com/mozilla/sccache/blob/main/docs/Architecture.md) uses a local server for both its server-side and client-side modes. The campaign forbids a new service, so the sccache pilot was not run or added. There are no sccache hit, miss, overhead, or timing results. This is a constraint-based omission, not evidence that sccache is slower.

## Development shell

The optional flake locks nixpkgs at the revision in `flake.lock`. Muon is 0.7.0, Meson 1.12.1, Samurai 1.3, Ninja 1.13.2, and pkgconf 3.0.10. The pkgconf source has the existing project's version and an ISC license. The Linux x86-64 pkgconf executable was 58,456 bytes and its Nix wrapper was 860 bytes in the test environment. These tools are development inputs and add no runtime dependency to the player.

Nix 2.35.4 evaluated both shell definitions with `nix flake check --no-build --all-systems`. The x86-64 Linux shell ran under emulation in a disposable Linux container. Its `pkg-config` resolved a controlled `.pc` file, and `make -n linux` expanded identically inside and outside the shell. The shell did not expose a C compiler in that container. The Linux player build remains in the existing Alpine container.

The macOS shell was evaluated but not entered on macOS because Nix is not installed there. Its use of the selected Xcode compiler and SDK still needs a native check. Nix's first shell setup fetched its closure and built pkgconf; provisioning time and disk use have not been measured. No Player artifact size, memory, startup, or build-time comparison has been attributed to the shell.

## Build measurements

The owner waived performance gates on 2026-11-10. The observations below were collected on the same macOS arm64 host, but under competing load: the one-minute load average was roughly 9–15 on ten logical CPUs during the native runs. The host state changed during later Rust runs. These numbers describe the runs; they do not establish a speedup under normal development conditions.

The reference for native dependencies was `ead8703`, the original revision plus the clean-prefix fix. The candidate was the **unaccepted** prototype at `campaign/build-cache` (`01ebc0c`), which still fails the direct Cargo validation requirement. Each used a separate empty prefix, warm copies of the same pinned source archives, Apple Clang, Homebrew Meson 1.12.1, and Ninja 1.13.2 through a `ninja -j 2` wrapper. `JOBS=2` was set; the wrapper enforces the actual Ninja limit. No native compiler cache was configured. Wall and child CPU times came from `/usr/bin/time -l`, with user and system CPU added. Copying the already-downloaded archives took 0.12 s and 0.11 s respectively on this filesystem; this is not cold network provisioning.

The five warm native runs alternated reference and prototype with the same tool environment. A first attempted warm prototype run changed `PATH` when the shell changed directories, selected a different Python, and began rebuilding SPIRV-Cross and libplacebo; it was interrupted and excluded. A direct invocation in the original environment then hit all six components. The prototype validates by hashing tools and component products, so its additional warm work buys checks the stamp-only reference lacks; it is not an equivalent integrity guarantee.

Five subsequent alternating macOS runs per side changed the Metal backend's log string in the libplacebo patch on every iteration. Both sides used the same patch changes, warm archives, Apple Clang, Meson, and the two-job Ninja wrapper. The reference included the clean-prefix and read-only reinstall fixes. Each build succeeded, and the resulting libplacebo library contained the intended string. The reference invalidated all six stamps and rebuilt SPIRV-Cross and libplacebo. The prototype reported hits for the other five components and rebuilt libplacebo. Reference wall time had a 33.05 s median and a 31.72–33.69 s range. Prototype wall time had a 13.44 s median and a 13.04–13.96 s range. Median CPU time was 53.54 s for the reference and 20.57 s for the prototype, with ranges of 52.60–55.72 s and 19.83–21.19 s respectively.

These observations cover the native dependency command, not the subsequent application rebuild or a release. The host had ten logical CPUs and competing load. One prototype run lacks its initial load snapshot; its neighboring snapshots were near a one-minute load average of 6. No independent profile established the remaining limiter. The narrower rebuild plausibly accounts for much of the difference, but the two sides do different validation work and the prototype remains unsafe for fresh direct Cargo use. These runs demonstrate potential for the native edit workload, not an accepted end-to-end speedup or a release-ready cache.

Five later alternating pairs included both `scripts/build-deps.sh` and `scripts/build.sh` after each real Metal log-string patch edit. Reference wall time had a 35.23 s median and a 35.06–35.29 s range; prototype wall time had a 28.08 s median and a 27.32–28.20 s range. Median CPU time was 57.48 s and 43.27 s, with ranges of 57.08–57.86 s and 42.40–43.51 s. All builds succeeded. Each resulting library contained the edited string, and dyld reported that the player loaded that library. The reference invalidated all six native stamps and rebuilt SPIRV-Cross and libplacebo. The prototype rebuilt libplacebo and reported hits for the other five components.

The application rebuild reduced the difference seen in the dependency-only runs. Cargo reported about 1.1 s per reference rebuild and 10.9–11.7 s per prototype rebuild after publication. Across the five runs, kache recorded 25 local hits and five duplicates for the reference, versus five local hits, 25 duplicates and five misses for the prototype. Each duplicate and miss ran a compiler. The prototype recorded identical tool policies for these five pairs. Earlier transition pairs were excluded because their `PATH` or SDK environment differed; two prototype transitions also rebuilt SPIRV-Cross. The controlled runs used separate kache salts, two-job limits, warm archives and prefixes, and the same effective environment on both sides. Their one-minute load averages ranged from 5.66 to 6.78 on ten logical CPUs. No independent profile established the remaining limiter. These observations do not establish equivalent integrity or an accepted speedup: the reference trusts stamps and the prototype still misses validation on fresh direct Cargo invocations.

For the accepted-code release, `scripts/release.sh` used `CARGO_BUILD_JOBS=2`, `KACHE_KEY_SALT=player-benchmark-clean-release-20261110`, and the native settings above. The first release attempt on the reference compiled Rust but failed when the bundler tried to strip a read-only copied library. Commit `8874813` fixes that failure, restores the copied files' original modes after signing, and was verified with the real release gate and `codesign --verify --deep --strict`. The clean accepted-code run includes native compilation, Rust compilation and bundling; it excludes archive downloads and host tooling installation.

The development run used `scripts/build.sh`, `CARGO_BUILD_JOBS=2`, and a distinct `KACHE_KEY_SALT=player-benchmark-dev-20261110`. Its first build took 57.61 s wall and 108.55 s CPU. An unchanged second build took 0.38 s wall and 0.28 s CPU; it emitted no kache compiler events. The kache event log filtered to this checkout recorded two `miss` events and two compiler runs for the edited build, `player_app` and `player`. The clean release recorded 65 `dup`, 23 `miss`, and 8 `passthrough` events; `dup` events each recorded a compiler run, so they are not counted as cache hits. The initial development build recorded 72 `dup`, 16 `miss`, and 5 `passthrough` events. These event labels and counts describe kache's records, not a comparison against an uncached build.

Five later alternating Rust-edit runs per side used the reference and unaccepted prototype checkouts above. Each changed the same help-text string in `player-app`, ran `scripts/build.sh` with two Cargo jobs, and verified the changed string in the resulting `--help` output. Both started from built development targets and warm runtime and native prefixes. Each side used its own kache salt; their built executables had rpaths in their respective checkouts. Reference wall time had a 4.51 s median and a 4.24–4.51 s range; prototype wall time had a 4.48 s median and a 4.36–4.53 s range. Median CPU time was 7.10 s and 7.07 s, with ranges of 6.74–7.14 s and 6.92–7.15 s. The difference is within the observed spread. For each edit on each side, kache recorded one miss and compiler run for `player_app` and one for `player`; the logs showed no native compilation. The host's one-minute load average was about 5.6–6.1 on ten logical CPUs. No independent profile identified the remaining limiter, and the prototype's fresh Cargo path can skip native validation, so these results do not establish equivalent correctness or a release-ready cache.

After the development build and tests warmed that kache store, a build into a new `CARGO_TARGET_DIR` with the same salt took 9.90 s wall and 15.66 s CPU. Its checkout-filtered events recorded 32 `local_hit`, 6 `dup`, 1 `miss` and 4 `passthrough` results; the six duplicates and one miss each ran a compiler. The installed player reported the original help text, used this checkout's native and FFmpeg rpaths, and played the fixture. This exercises compiler-cache restoration into a fresh target; it is not equivalent to Cargo's unchanged local-target reuse or to a GitHub Actions restore.

The accepted-code release's `scripts/measure.sh final` reported a 1,699,056-byte executable, 14,693,984-byte executable-plus-framework closure and 69.95 MB median 1080p RSS; all of its size, memory, protocol, Lua and audio checks passed. The first attempt stopped because the isolated checkout lacked `audio-mp3.mp3`; the second used that fixture generated with the repository's exact recipe. The script exited 75 because its internal host check deferred timing checks. The owner waived the gate, but the reported timing samples remain subject to contention and are not a performance pass. Its revision label included `-dirty` because the separate development help-text experiment was still present; the release binary had been built and signed before that edit. After restoring the experimental edit, `scripts/audit.sh` passed its 16 FFmpeg, 7 build, 56 local-only and 20 release checks; it skipped the advisory scan because `cargo-audit` was not installed. `tests/run.sh suite` passed 458 checks, including Metal and Vulkan GUI gates. Its first fixture-generation attempt timed out while FFmpeg was waiting; the harness retried and succeeded, so that intermittent fixture issue remains unresolved.

Two independent macOS release builds of `8874813` used the same tools, build policy, two-job limits and warm source archives, but separate checkout paths, path-valued flags and distinct kache salts. The second completed in 88.01 s wall and 136.97 s CPU, and also passed all 20 release checks and strict signature verification. Their bundles had the same 16 paths, types, modes and symlink targets, but were not byte-identical: `player`, `libplacebo.387.dylib`, `Resources/build.json` and `CodeResources` differed. The other three bundled libraries and remaining files matched. The player had 79 differing bytes and libplacebo 48; all those differences lay in their Mach-O UUID or code-signature regions. The build stamp hashes the unbundled player, whose recorded hash differed; those unbundled binaries contain their respective absolute checkout rpaths. No artifact bytes were normalized, and this is not a claim of byte-reproducible releases.

The Linux dependency and application builds ran under x86-64 emulation in the pinned Alpine container as correctness checks; they are not comparable to native Linux CI timing. The image lacks kache and mold, so these runs supplied workspace-local kache 1.0.0 and mold 2.39.1, with a compiler wrapper selecting mold and the existing flags preserved. No additional cache service was started. The local Linux release script built the tarball and checked its checksum. A separate closure audit passed without the tool setup's `LD_LIBRARY_PATH`. The full `tests/run.sh suite` then passed 427 checks, including headless Wayland, playback, the Rust-link gate and the audit. The tested Linux inputs matched the accepted tree at `a7cb1f3`. Mold's local `.got` slots initially triggered a false static-FFmpeg finding; that commit limits the exception to local object slots in `.got`, and its regression fixture still rejects defined FFmpeg symbols elsewhere. The follow-up `7690535` was verified with the same real audit and a fixture that forces ELF inspection failures.

`scripts/linux-container.sh scripts/measure-linux.sh final campaign-emulated-20261110` measured that existing release under the same emulation. The stripped executable was 9,614,552 bytes; median 1080p RSS was 71.13 MB across seven playback runs, and idle RSS was 9.6 MB. The script found 12 dynamic dependencies and only the `file` protocol. The timing readiness tool was unavailable in the container, so the script deferred its timing gate. Emulator overhead limits the RSS result as evidence for native Linux. The script wrote an empty revision field in its temporary worktree, so these results are tied to the release and inputs described above rather than that field. The generated metrics row was not retained as a native Linux measurement.

A second emulated Linux release build used the same Linux build inputs, container path and tool settings, with fresh target and kache directories. The first checkout was at `88553d6` with the audit fix applied; the second was at `93f762b` with that fix committed, so the revisions differed even though the Linux build inputs matched. Cargo reported that the kache-wrapped `rustc` command for `player-overlay` terminated with `SIGBUS`. That report does not establish whether kache or its compiler child received the signal. An isolated build of that crate with the same target and flags then succeeded. Disk and memory were available, but the signal's cause was not established; kache also warned that the workspace cache is on FUSE, which is not proof of the cause. No second tarball was produced, so Linux release reproducibility remains untested.

Under that emulation, isolated native dependency builds used Meson 1.12.1, Samurai limited to two jobs, the same compiler wrapper and warm source archives. `/usr/bin/time -v` inside the container measured the build process; an outer host timer also included the existing Docker image check and container startup. A clean reference prefix took 49.11 s inside (85.94 s CPU) and 51.58 s end to end; the unaccepted prototype took 51.15 s inside (87.57 s CPU) and 52.63 s end to end. These are single observations, not a speedup comparison.

Five alternating unchanged Linux builds had a 0.14 s median inside the reference container (0.14–0.15 s range), versus 1.50 s for the prototype (1.47–1.52 s). Including container startup, the medians were 1.33 s and 2.68 s. None compiled or installed products. The reference trusted stamps; the prototype validated the cached artifacts and tools. After the same blank-line edit inside the libplacebo recipe, the reference cleared its prefix and rebuilt all three components in 48.58 s inside (85.00 s CPU); the prototype reused Vulkan headers and Shaderc and rebuilt libplacebo in 50.67 s (87.21 s CPU). These are single contended emulated runs, but they show why a narrower closure alone is not evidence of a worthwhile improvement when libplacebo dominates the work.

A local restore simulation copied the prototype's complete Linux cache and prefix link to another checkout mounted at the same `/work` path. The filesystem copy took 0.36 s; validation and three hits took 1.72 s inside the container and 3.64 s including startup. After corrupting the copied Shaderc archive, the prototype detected the mismatch, reused Vulkan headers, rebuilt Shaderc and libplacebo, and restored the original archive hash. That rebuild took 51.51 s inside (88.03 s CPU). This exercises the unaccepted prototype only: it is not a GitHub Actions restore measurement, and the existing CI cache paths have not been adapted to this cache layout.

Native Linux timings and qualification, a restored CI-cache measurement, equivalent before/after Rust and release comparisons, and F1 qualification remain open.

## Kache Cargo guard prototype

The kache fork's local branch `campaign/player-native-guard` adds an opt-in workspace guard at `f6aef379`. Its focused Cargo-proxy tests passed 12 cases and Clippy passed; the existing test that explicitly starts a daemon was excluded under the campaign's no-new-service constraint. That revision selected a workspace before Cargo expanded aliases. A real Cargo alias configured outside a guarded workspace selected that workspace's manifest without running its guard, so that revision did not satisfy the full reader boundary. Neither the fork branch nor the Player prototype is integrated into CI. Two exploratory test runs inadvertently started separate kache daemons; both were stopped. Subsequent tests used the fork's `KACHE_DAEMON_AUTOSTART=0` setting.

A second, unaccepted Player prototype at `campaign/build-cache-shim` (`d300093`) used that guard on macOS arm64, with warm pinned archives, Meson 1.12.1, Ninja 1.13.2 limited to two jobs, and the fork's debug compiler shims. These observations were collected during implementation, before the final Objective-C and compiler-shim identity checks in that commit. The initial dependency build took 43.04 s wall and 68.99 s CPU. An unchanged dependency build took 0.64 s wall and 0.60 s CPU and reported six hits. A fresh direct `cargo build` through the shim compiled nothing; after a Vulkan header was altered, the same command rejected the cache, and after the header was restored it again compiled nothing. An audit started without the dependency build's tool settings stopped at its build gate with a policy mismatch; the matching `tests/run.sh build` gate passed all seven checks after the identity changes. The rest of that audit was not run for this prototype. Host load was not recorded for these observations, and they are not a comparative speedup claim.

Appending a blank line to the libplacebo patch caused only libplacebo to rebuild: 19.55 s wall and 30.33 s CPU for the dependency command, followed by a 9.58 s wall and 17.94 s CPU Cargo build that recompiled six Player crates. Restoring the patch produced the same native closure in 19.29 s wall and 30.09 s CPU, followed by a 9.76 s wall and 18.24 s CPU Cargo build. This is a controlled fingerprint change, not a functional source edit or release qualification. At that point the prototype also needed native Linux qualification, CI provisioning of a guard-capable kache, and resolution of the outside-alias boundary before C1 could be accepted.

The synthetic cache suite passed 55 tests on macOS; a subsequently added restored-cache case also passed separately. In the existing Alpine x86-64 container under emulation, 44 cache and recipe tests passed with four macOS-only cases skipped, and the restored-cache case passed separately. The latter copied a cache, validated unchanged reuse, then corrupted a restored product and checked that its owner and dependent rebuilt. These fixtures do not establish compatibility of the real Linux native build or application.

The later candidate through `cbce2f6` also built the real Linux dependencies and application in that emulated container. To obtain the fork's Linux binary without starting a daemon, its bootstrap used the existing kache wrapper with caching explicitly disabled; the binary used for Player was then rebuilt with mold 2.39.1 and ran with `KACHE_DAEMON_AUTOSTART=0`. The cache fixture command ran 56 cases without failures, including eight platform-specific skips. A one-time kache FUSE warning initially caused an unnecessary libplacebo rebuild because it was included in the compiler-version text; `cbce2f6` filters that diagnostic, after which two dependency runs reported three hits each. A fresh Cargo build compiled nothing, rejected an altered Vulkan header, and compiled nothing after its restoration. The real Linux closure audit passed with the build-only `LD_LIBRARY_PATH` removed. These results are emulated correctness checks, not native Linux qualification or a performance comparison.

The existing `tests/run.sh suite` then passed 427 checks in the same emulated environment, including headless Wayland, playback and the guarded Cargo workspace tests. No kache daemon was observed in the container. The suite used the mold runtime library path for its build tools; the separate closure audit above was run without it.

At `77fe78a`, the isolated candidate additionally tracks the appearance and pkg-config metadata of Linux `libunwind` and `libxxhash`, and republishes changed policy metadata even when products can be reused. The focused command ran 62 tests on macOS with one Linux-only skip and 59 in the emulated container with eight platform-specific skips; neither run failed. The updated native dependency command rebuilt libplacebo on Linux and then reported three hits; on macOS it rebuilt SPIRV-Cross and libplacebo and then reported six hits. The macOS development build gate passed seven checks. The 427-check Linux suite predates these policy-only changes. CMake discovery and optional library and header content remain unresolved, so these results do not accept C1.

The kache fork through `521f6fe1` resolves the tested external aliases before selecting the guard and stops workspace discovery at an independent nested workspace. Its focused proxy tests passed 18 cases on macOS and 19 under x86-64 Linux emulation; one daemon-starting test was excluded on each. Clippy passed on macOS. A real Cargo 1.92 experiment showed that the inspection process could load an unstable configuration include ignored by the actual command, allowing a plugin to bypass the guard. Configured alias inspection now fails closed on Cargo versions older than 1.94; the same experiment then rejected the command.

With the updated fork and Player prototype `f8f6106`, changing the kache engine rebuilt SPIRV-Cross and libplacebo while the four other macOS components hit. An alias configured outside Player rejected a corrupted Vulkan header. After restoration, the first build recompiled 11 Rust crates following publication; the next unchanged build compiled none. These are correctness observations, not a release qualification. The actual libplacebo cache remains unsafe for optional system input changes: a Linux fixture changing a transitive `xxhash.h` include without changing its pkg-config metadata was accepted. CMake discovery and CI provisioning remain unresolved.
